# 世界观候选审查

## 目的

把对话中正在形成的世界观方案当作**尚未获得作者批准的候选**，在进入正史或持久化工程前完成反方审查与修订收敛。审查对象可以来自奇幻、科幻、架空历史、现实主义地方社会、游戏世界或其他题材；不要默认存在魔法、国家、民族或现代制度。

## 所有权边界

- 本 Skill 拥有 `conversation-only` 候选的提取、质疑、比较、修订与取舍建议。
- `$worldbuilding-engine` 拥有持久化世界状态、候选文件、真实性工程、迭代检查点和正典晋升门禁。只有用户要求持续项目、写入文件或晋升时才交接。
- `fiction-core-zh:world-architect` 拥有完整世界设定的实质创作与大规模重构。
- `fiction-core-zh:story-editor` 拥有故事、场景或正文的编辑诊断。

审查请求默认只报告和提出候选修订，不修改文件，不晋升正史。

## 权威与状态

按以下顺序约束候选：用户本轮明确指令 → `anchored` → `canon` → 已批准故事约束 → 对话候选 → 本轮新建议。

仅作者可以把内容标为 `adopted`／`canon`。以下均不等于采用：

- 用户说“继续”“完善”“再推演”；
- 用户未反对；
- AI 在后续回答中继续使用；
- AI 称某版为“最终版”；
- 候选已经详细、完整或通过审查。

候选状态使用：`conversation-only`、`under-review`、`recommended`、`rejected`、`superseded`。若作者明确采用，再由项目协议处理 `adopted`／`canon`。

## 选择最小充分档位

- `quick`：一项或少量候选；交付最重要的 1—3 个问题与最小修复。
- `full`：用户要求逐项、全面、严格、反向审查，或候选之间存在明显依赖；读取 [深度审查框架](references/audit-framework.md)。
- `repair`：用户明确要求完善、重写或推翻；先完成审查，再只修最高优先级根因。

不要把一次局部质疑扩成全世界百科审计。

## 工作流

### 1. 确认材料范围

优先读取当前可见对话历史，再读取用户指定的正史、项目文件或参考资料。若历史被截断，列入 `missing_context`；只有缺失内容会改变核心判断时才请用户补充，不得自行重造旧结论。

### 2. 重建最小候选账本

从对话中提取本次审查实际涉及的候选：

```yaml
- candidate_id:
  content:
  source: user | assistant | mixed
  conversation_evidence:
  status:
  intended_function:
  role:
  not_equivalent_to: []
  relation_claim:
  dependencies: []
  alternatives: []
  conflicts: []
```

不要把相邻构想自动合并，不要用较新版本静默覆盖旧版本，不要把 AI 的推断归给作者。候选很多时先聚类，再审查上游前提和高影响项。

### 3. 保护作品意图

在批评前简述：这些候选试图解决什么、承诺何种体验、最有效之处是什么、哪些优势不可因修订而丢失。不要用终稿标准攻击早期灵感，也不要以“仍是草稿”为结构性问题开脱。

### 4. 审查根因

最低检查：

- 是否违反锁定事实或彼此矛盾；
- 是否把源头、中枢、操作者、后继者等不同角色坍缩成同一事物；
- 是否把功能相似误写成血统、法统、权限或技术继承，或以后世用途倒推古代唯一目的；
- 是否从底层条件推出资源、权力、生活与历史后果；
- 删除专名后是否仍可辨认，还是现实／类型模板换皮；
- 冲突是否真正不可兼得，还是预设了一方正确；
- 是否进入普通人的生活、身体和关系；
- 是否能形成场景，而非只能被旁白解释；
- 是否给人物留下选择和改变解释的空间；
- 复杂度是否超过当前故事能兑现的容量。

每个 finding 使用：`证据 → 问题 → 读者／故事影响 → 根因 → 修复`。不要用“不够有张力”“可以更丰富”等无证据判断。

### 5. 沿修订阶梯收敛

依次尝试并停在最小有效层级：

1. 删除不需要存在的候选；
2. 复用或合并已有机制；
3. 澄清边界、成本、排除者或失败方式；
4. 从底层前提重新推导；
5. 局部重构；
6. 只有以上无效时才增加新设定；
7. 若仍不成立，明确推翻重做。

详细不等于成熟；不要用更多专名掩盖薄弱因果。

### 6. 反驳自己的修订

修订后至少检查：是否只是换成另一种现实模板；是否为了新鲜而随机怪异；是否逻辑更完整却更难进入场景；是否增加无用复杂度；是否削弱原有魅力；是否预写了主题答案；删除主角后世界是否仍会行动。

若反驳成立，直接执行第二轮修订，不只在结尾承认问题。

### 7. 保持候选状态

交付时分开列出：保留、修改、合并、拒绝、被替代和新生成候选。新方案最多升到 `recommended`，等待作者裁定。

## 输出

按任务规模缩放。完整审查默认包括：

1. 审查范围与创作目标；
2. 候选账本；
3. `protected_strengths`；
4. 按严重度排序的 findings；
5. 最小修订，必要时再给激进重构；
6. 对新方案的反向审查与第二轮修订；
7. 候选状态变化与作者待决项。

结尾使用：

```yaml
assumptions: []
missing_context: []
protected_canon: []
candidate_changes:
  preserved: []
  revised: []
  merged: []
  rejected: []
  superseded: []
new_conversation_candidates: []
requires_author_decision: []
proposed_canon_diff:
  additions: []
  modifications: []
  deprecations: []
```

`proposed_canon_diff` 只是可能的采用清单，不代表已经写入正史。
