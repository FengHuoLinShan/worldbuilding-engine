# 持续迭代协议

## 1. 何时启用

用户要求“持续完善”“继续多轮”“从既有成果继续”“整理全部历史再迭代”，或一个 `candidate`／`instance` 已经经历多轮扩建时，启用本协议。它是工作节律，不是新的深度档位；每轮仍使用 `expand`、`audit` 或 `repair`。

先读实际历史、当前权威工件和未决入口，再决定下一轮。不要只读最后一份总结，也不要把历次输出逐篇重做。

## 2. 分开权威与持久化

内容状态与写入位置是两条轴：

| 轴 | 状态 | 含义 |
|---|---|---|
| 权威 | `draft`／`proposed`／`canon`／`author-required`／`deprecated` | 这项内容有多大效力 |
| 持久化 | `conversation-only` | 只在对话中形成候选，不写文件 |
| 持久化 | `candidate-files` | 可持续写入项目允许的候选页、提案、变更记录和索引，但不得晋升正典 |
| 持久化 | `canon-files` | 仅在明确采纳及项目正典流程授权后写入正典面 |

“继续完善，无需每轮确认，但暂不写入正史”应解释为 `candidate-files`，不是 `conversation-only`，更不是 `canon-files`。该授权在目标或边界改变前持续有效，不要每轮重复索取确认。

若项目有机器状态，可选地使用现有开放字段，不修改 schema：

```json
{
  "extensions": {
    "iteration": {
      "goal": "持续目标",
      "persistence_scope": "candidate-files",
      "round": 4,
      "checkpoint_every": 3,
      "last_checkpoint_round": 3,
      "active_slice": "地图—机构—家庭—时间线纵切",
      "locked_invariants": [],
      "non_goals": []
    }
  }
}
```

已有 Vault、Wiki 或仓库自己的元数据时，复用其目标、状态和变更记录；不要为了本协议创建 `world-state.json`。

## 3. 先做历史压缩

把多轮历史压成一张差异账，而不是摘要合集：

1. 哪些底层规则与尺度已经锁定；
2. 哪些候选曾被修改、撤回或晋升；
3. 哪些人口、地图、设施、家庭和时间分母必须继续共用；
4. 哪些缺口反复出现，说明问题在接口而非篇幅；
5. 哪些检查结果只是历史快照、未完成或不可靠，不能冒充当前证据；
6. 下一轮怎样改变一个真实选择、场景、依赖或矛盾。

只保留能影响下一轮的历史。重复的中间措辞、过时统计和已被总稿吸收的草案不进入工作上下文。

若期间发生过正典晋升或集中裁定，把差异账展开为“主张—当前状态—当前权威证据—旧状态来源—动作”。最新明确裁定高于当前总入口，总入口高于领域页，领域页高于候选页；日期变更记录和旧日志不回写为“当时已经采用”，也不能因保留旧措辞而让当前页继续宣称 blanket candidate。

### 3.1 分段采纳

作者按编号、章节或明确主张采纳时，先把被点名部分拆成原子命题，只晋升这些命题。相邻段落可以作为理解上下文，但仍保持 `proposed`／`author-required`；其中的开放问题、具体人物、时序、组织名和结局不得因“整体方向已采用”而顺带关闭。

记录时同时列出：本轮已采用、仍为候选、明确排除、继续开放。`canon_diff` 继续只使用 `additions`／`modifications`／`deprecations`，不为分段采纳增加机器字段。

### 3.2 替换级正史迁移

当新设定改变现行地图、历史底盘、文明功能或其他权威解释时，按以下顺序迁移：

1. 指定新的现行权威入口及其覆盖范围；
2. 盘点旧权威中的原子主张和直接引用者；
3. 用 `KEEP`／`NARROW`／`EXPAND`／`REGROUND`／`REASSIGN`／`DEPRECATE`／`KEEP OPEN` 建立可读差异账；
4. 只同步直接受影响的现行领域页、索引和依赖，不借机重写无关设定；
5. 旧变更记录、日志和时间切片继续保存形成史，不反向伪造当时状态；
6. 保留新权威没有回答的开放问题，并把失效的下游交给对应工件所有者复核。

这些动作只用于报告和迁移判断，不进入 `world-state` schema。项目自己的 Worldcheck、Vault lint 或其他正式门禁由宿主调用；引擎只记录本轮运行范围与结果，不复制项目验证器。

## 4. 每轮只选一个纵切

不要按二十二面顺序补百科。选择能同时闭合至少两条既有链、且能落到同一实例的最小纵切：

```text
空间位置 → 资源／设施 → 组织／权利 → 家庭／身体
→ 普通日 → 故障 → 历史沉积 → 下一代反馈
```

每轮只采用一个主动作：

- `expand`：补真正缺失的机制；
- `connect`：把已有机制接到同一人口、地图、机构、家庭或时间线；
- `pressure`：让既有系统经历故障、跨境、贫困、代际或反事实；
- `consolidate`：删除重复解释、统一数字、收紧状态和审查入口。

优先选择复用既有规则、地点、机构和家庭夹具的纵切。只有新对象会改变因果或场景时才命名；不要用新专名制造进度感。

## 5. 四项必检

### 5.1 魔法或技术扩散梯度

分别检查：能力是否存在、训练能否代际持续、民生覆盖到哪里、冲突／应急改式有多强。会用不等于会教，会教不等于普及，战场改式强也不等于生活应用发达。每项都要回到成本、维护、权限、最后一里和责任。

### 5.2 唯一性与最高级断言

对“唯一”“最发达”“最开放”等断言写明：比较范围、操作性判据、已知世界说法与作者层事实的区别、可能推翻它的反例。不能靠让其他地区集体愚昧来证明本地独特。

### 5.3 时间尺度惯性

成熟城市、制度和文明应同时通过两档测试：十年内哪些骨架因资本、设施、地权、训练和代际惯性而相对稳定；百年内哪些河道、道路、产业、人口、权力和认同必然换形。变化需要载体和触发，不得十年一换首都，也不得百年毫无沉积。

### 5.4 横向完整与纵向可用

当通用成熟度显著高于实例成熟度，停止继续补框架。下一步至少选择“一张可行走的工作地图、一个可办理事情的机构、一个受影响的家庭、一个完整时间过程”中的两个，并让它们共用分母。

## 6. 候选山与停止条件

出现以下任两项，视为“候选山”：

- 二十二面都有段落，但人物仍无处可站、无事可办；
- 每轮新增一章和一批专名，却不改变旧结论；
- 未决问题增长快于已关闭问题；
- 通用成熟度比实例成熟度高两级以上；
- 同一事实散落在多份候选稿，数字和状态开始漂移；
- 下一轮只能回答“还有什么可以补”，不能说明会改变哪项选择或压力。

触发后不得继续横向扩写。执行一次 `consolidate`：统一权威总稿、复用或删除重复页、压缩审查入口，并转向地图、机构、家庭、案件、年度或一生等纵向实例。若下一项工作不会改变场景、选择、依赖、矛盾或采用判断，把该面标为当前范围已饱和。

## 7. 验证节律

每轮只做与改动相称的定向检查：元数据／schema、所改链接与 ID、数字闭合、受影响依赖、项目规定的语义复核。

持续候选工程默认每三轮设置一次全量检查点；项目或用户另有节律时服从其规则。以下情况不等待轮次，立即做全量检查：

- 正典晋升或正式交接；
- 核心规则、schema、术语契约或依赖拓扑改变；
- 多个共享入口完成合并；
- 项目门禁明确要求。

一次检查没有可靠结束，不要为了得到漂亮数字反复重跑，也不要沿用旧轮次结果冒充当前结果。记录为 `not-run`、`incomplete` 或 `unreliable`，继续保留上次检查点的日期与范围。

`world_audit` 会读取可选的 `extensions.iteration`，给出 `checkpoint_due` 与框架／实例饱和提示；它只提供节律建议，不替宿主运行项目自己的验证器。

## 8. 共享写入与并发

默认一个任务拥有共享正典入口的写权。持续轮次先修改领域工件，索引、总入口、依赖图、日志和全量报告在检查点一次合并。若现场已有并发修改，先划分文件所有权或串行合并；不要自行给其他任务发指令、等待或建立协调网，除非用户明确要求。

## 9. 整理、采纳与交付

用户要求“整理全部成果”时先执行总审：统一分母、删除重复、标出被替代内容、核对最高级断言、收敛作者必决项，再写最少的权威候选工件。写入候选 Wiki 不等于采纳正典。

正典集中晋升或全量交叉修复后，必须在同一检查点同步当前领域页、总入口、实体／概念索引、依赖图、变更记录和项目要求的日志／热缓存；旧变更记录只保留形成史。同步前按历史因果、交通通信与知识扩散、势力授权关系逐项复核，避免用一次状态替换掩盖新的宏观冲突。

每轮交付只报告：本轮改变了什么；哪些仍为候选／作者必决；实际修改文件；定向或全量检查状态；下一个最高收益纵切。不要把重复的页数、链接数和旧测试快照写成成果主体。
